# 更好的 Minecraft 商店 · better-minecraft-shop (bmcs)

> **本文件是仓库内的深度技术说明**（`docs/技术说明.md`）：
> 面向开发者，讲清架构、协议与实现依据。
> 面向使用者的**中英对照安装 / 使用说明**在仓库根目录 [`README.md`](../README.md)。

Minecraft **1.21.1** / **NeoForge 21.1.x** / Java 21 的数据驱动商店模组。
以 **FTB Library** 为唯一 UI 前置，在背包界面左上角提供侧边栏入口（另可**按 O 键**打开）；
内置单一货币 **深索币**；商品价格与限量全部由服务端 JSON 配置驱动 ——
**1.0.5 起买卖分成两个平级目录**：`config/better-minecraft-shop/in/` 放买入商品（`price` + `stock`），
`config/better-minecraft-shop/out/` 放卖出商品（`sell_price`），各自支持任意数量、可递归的配置文件，
单文件损坏只跳过该文件，同一目录内重复项按分类优先级去重，跨目录则做「卖价不得高于买价」的防刷钱校验；
首启只建空目录、**不写默认 JSON**。界面用**虚拟滚动**支撑 10000+ 条目，网络按 **500 条一批**分批同步，
配置文件改动会被 **WatchService 热重载**自动生效；单人存档里任何人都能（专用服务器需 OP）在**编辑模式**下用背包物品新建分类 / 商品，保存即落盘。

本模组的实现参照了已归档的 SDMShop 3.3.1（反编译分析见 `docs/SDMShop-缺陷对照表.md`），
但**逐条重写**、不复制其代码，并针对性修掉了它的崩溃 / 坏档 / 元数据丢失问题。

## 二、依赖与构建

### 2.1 前置依赖坐标（真实可用，非编造）

```
FTB Library (NeoForge 1.21.1 线)：https://maven.ftb.dev/releases
    坐标：dev.ftb.mods:ftb-library-neoforge:2101.1.37
Architectury API（FTB Library 的强制前置）：13.0.6
    坐标：dev.architectury:architectury-neoforge:13.0.6
```

本项目对这两个前置支持**两种依赖方式**（`build.gradle` 自动判断）：

1. **`libs/` 下放了官方 jar** → 用本地 jar（`compileOnly` + 开发环境 `runtimeOnly`），
   好处是**内网/离线也能构建**，且发布时不会把前置模组打进本模组的 jar：

   ```groovy
   dependencies {
       compileOnly files("libs/ftb-library-neoforge-2101.1.37.jar")
       compileOnly files("libs/architectury-13.0.6-neoforge.jar")
       runtimeOnly files("libs/ftb-library-neoforge-2101.1.37.jar")   // 只为 runClient/runServer
       runtimeOnly files("libs/architectury-13.0.6-neoforge.jar")
   }
   ```

2. **`libs/` 为空** → 回退到官方 maven 坐标（仓库已配在 `settings.gradle` 的
   `FTB Maven` / `Architectury Maven`）：

   ```groovy
   compileOnly "dev.ftb.mods:ftb-library-neoforge:2101.1.37"
   compileOnly "dev.architectury:architectury-neoforge:13.0.6"
   ```

仓库**不包含**这两个 jar（FTB Library 为 All Rights Reserved，`libs/*.jar` 已被 `.gitignore` 忽略），
获取方式见 `libs/README.md`。

### 2.2 仓库配置（本机踩过的坑，已固化）

`settings.gradle` 用 `dependencyResolutionManagement` + **`RepositoriesMode.PREFER_SETTINGS`** 统一声明仓库：
复刻 moddev 插件内部的两个仓库（`Mojang Meta`、`Mojang Minecraft Libraries`，名称/地址/元数据源/内容过滤
必须一致，因为 Gradle 的模块描述符缓存是按「仓库身份」命中的），再补可达镜像
（BMCLAPI、StellarDrift、Aliyun、Maven Central）。

原因（均为实测结论）：

1. moddev 插件会把 `https://maven.neoforged.net/releases/` 自动塞进项目仓库列表；本机该域名
   **DNS 被污染**，每次访问都要等到连接超时，几十个构件累加会让构建停滞几十分钟。
   `PREFER_SETTINGS` 让插件自动添加的项目级仓库不再参与解析。
2. `net.neoforged:minecraft-dependencies:1.21.1` **只存在于 `mojang-meta` 仓库**；
   `net.neoforged:neoform-runtime:2.0.24` 的实际可下载源是 StellarDrift 镜像。
3. 本机 Gradle 缓存里的 NeoForge / NeoForm 构件本来就是按这些镜像的坐标缓存的，**离线也能命中**。

### 2.3 构建与运行

```bash
cd bmcs
gradlew.bat build                 # 产物：build/libs/better-minecraft-shop-1.0.5.jar
gradlew.bat runServer             # 开发服务器（首次需 run/eula.txt 写 eula=true）
gradlew.bat runClient             # 开发客户端（按 O 键或点侧边栏按钮开商店）
```

**已实测**：`gradlew.bat build` → `BUILD SUCCESSFUL`，产物 `better-minecraft-shop-1.0.5.jar` 约 **746 KB**，只含本模组类与资源。

### 2.4 离线自检（不用启动游戏）

```bash
python tools/verify_assets.py .            # 配置/去重优先级/语言/侧边栏/架构不变量
python tools/check_jar.py build/libs/better-minecraft-shop-1.0.5.jar

python tools/gen_stress_config.py run/config/better-minecraft-shop/in 10000 --side=buy  # 造压力配置
```

## 三、核心设计

### 3.1 深索币（单一货币）

* 存储：NeoForge **Data Attachment**（`AttachmentType<DeepCoinAccount>`，注册于 `neoforge:attachment_types`），
  由 `DeepCoinAccount.CODEC` 序列化，随玩家实体存档；`.copyOnDeath()` 保证**死亡不掉落**。
* 余额恒在 `[0, 999999999999]`，入账用饱和加法，不会溢出。
* 转账「先扣后入」，入账异常则原路退回，总量守恒。
* 命令：`/bmcs balance`、`/bmcs balance <玩家>`、`/bmcs pay <玩家> <金额>`、
  `/bmcs set|add <玩家> <金额>`（权限 2）。
* 展示：`currency.better_minecraft_shop.deepcoin` = `"%s 深索币"`，千分位格式化。

> **为什么不是 DataComponent**：DataComponent 描述的是 **ItemStack** 的数据；玩家余额属于实体存档，
> 在 1.21.1 里对应 Data Attachment。本模组的物品数据**全程**用 DataComponent
> （`DataComponentPatch` 解析配置、`ItemStack.copy()` 传递、`isSameItemSameComponents` 匹配），
> 没有任何原始 NBT 读写。

### 3.2 数据驱动配置（多文件 + 去重 + 本地化）

* 目录：`config/better-minecraft-shop/in/**.json`（买入：`price` + `stock`）与
  `config/better-minecraft-shop/out/**.json`（卖出：`sell_price`），**任意数量、可递归子目录**；
  旧数据不自动迁移、只给提示（见第五节）。详细格式见第五节。
* **两个目录、两个栏位**：界面左侧「买入 / 卖出」分别只读 `in/` 与 `out/` —— 买入按 `price`
  结算并展示 `stock` 限量，卖出按 `sell_price` 结算且不限量；两个方向各自分类、各自去重定价。
* 首次启动只创建空的 `in/` 与 `out/`，**不写任何默认 JSON**；旧模板移到
  `docs/examples/legacy-shop_items/`，只作文档与迁移参考，不打进 jar。
* **单文件隔离**：一个文件 JSON 写坏 / 字段非法，只跳过该文件（或该条），其余文件照常生效，
  并打印精确到「文件 + 分类 + 第几条 + 原因」的日志。
* **10MB 上限**：单文件超过 10MB 直接拒绝加载并告警，避免 OOM。
* **跨文件去重**：同一件商品（判重键 = 物品 id + 附魔签名）
  在多处出现时，保留**分类优先级**更高的一份。优先级表：
  `武器工具(80) > 五金(70) > 建材(60) > 石材(50) > 木材(40) > 原材料(30) > 食物(20) > 种子(10)`，
  未知分类 5；分类可用 `priority` 字段显式覆盖。默认配置里**故意留了一条重复项**
  （`minecraft:stone` 同时出现在 04-stone.json 与 05-wood.json）用于验证该机制，启动日志会打印取舍结果。
* **热重载**：`WatchService` 监听整个配置目录（含子目录），事件静默 1.5 秒后
  回到服务端主线程整体重载，然后向在线玩家重新同步；也可以 `/bmcs reload` 手动触发。
* **本地化**：物品名不再写进配置（`display_name` 已移除，写了也会被忽略并提示），
  展示名一律由 `ItemNameUtil` 走游戏内置链路
  （`minecraft:custom_name` → `minecraft:item_name` → 物品翻译键 → 缺翻译时回退到可读文本），
  跟随**客户端语言**；分类名同样可以省略 `display_name`，用内置键
  `category.better_minecraft_shop.<分类id>`。排查名字问题用 `/bmcs debug item <物品id>`。

### 3.3 限量库存

* `stock: -1` = 不限量，不占任何持久化状态；`stock: N` = 限量，售出扣减。
* 存储：世界级 **`SavedData`**（`world/data/better_minecraft_shop_stock.dat`，格式 v2），
  内容用 `Codec.unboundedMap(Codec.STRING, Codec.INT)` 编解码：一张剩余量表 + 一张「上次看到的配置上限」表。
* 语义修正：**买入扣减、卖出回收补货（不超过配置上限）**；缺键时按配置初始值而不是 0。
* 「配置上限」与「管理员放量」的取舍（实测踩过坑后定的规则）：
  * 配置里的上限**没变** → 保留当前剩余量（`/bmcs stock set` 的放量不会被重载或重启吃掉）；
  * 配置里的上限**变了** → 立刻夹到新上限（服主把 100 调成 10 时马上生效，日志会提示收紧了几项）；
  * 旧存档（只有剩余量）→ 保留剩余量、不夹取，避免升级时把数据改小；
  * 卖出回收的上限取 `max(配置值, 当前值)`，所以玩家卖回商品不会把管理员的临时放量冲掉。
* 管理员：`/bmcs stock list | set <键> <数量> | reset <键>`。

### 3.4 交易（服务端权威 + 可回滚）

* 买入：校验数量/余额/库存 → **先给货**（放不下则把已放入的部分取回）→ 扣钱 → 扣库存
  （后续步骤异常则把货收回）。
* 卖出：**先真正移除物品**（组件精确匹配，且**只扫主背包 + 副手，不碰护甲槽**）→ 成功后才进账 → 回收补货。
* 金额一律 `Math.multiplyExact`，溢出即拒绝。

### 3.5 网络（StreamCodec）

| 包 | 方向 | 载荷 |
|---|---|---|
| `better_minecraft_shop:open_shop` | C→S | 无字段（`StreamCodec.unit`） |
| `better_minecraft_shop:shop_action` | C→S | `动作(BUY/SELL)` + `商品 UUID` + `数量` + `目录版本` |
| `better_minecraft_shop:shop_data` | S→C | 分批全量快照：`是否打开界面` + `目录版本` + `本人余额` + `批序号/批总数/条目总数` + 分类（仅第 0 批）+ 本批商品（≤500 条） |
| `better_minecraft_shop:shop_patch` | S→C | 交易后增量：`目录版本` + `本人余额` + `商品 UUID` + `新剩余库存` |

要点：

* 商品用 **UUID 寻址**（由配置键派生的 v3 UUID，跨重启稳定），**不用列表下标**；
* 交易包附带**目录版本号**，版本不符直接拒绝并要求重开界面；
* 数量在**解码阶段**就做范围校验（`0 <= qty <= 4096`），服务端再按商品收紧一次；
* `ItemStack.STREAM_CODEC` 传输模板，附魔 / 改名等组件原样过网；
* **分批同步**：全量快照按 500 条一批连续发送（10000 条 = 20 批），
  客户端在 `ShopClientData` 里累积、收齐最后一批才装配并打开界面 ——
  原版自定义载荷有 1MB 硬上限，单包塞 10000 条会被踢下线；
* **增量补丁**：交易完成后只发这一件商品的新库存 + 我的余额，
  不再像 SDMShop 那样「每笔交易全量重推」（10000 条目录下那是几百 KB 的浪费）；
* 界面刷新只发**发起交易的那名玩家**（不是全服广播），也不会每笔交易都写盘。

### 3.6 商店 GUI

* 框架：FTB Library 的 `BaseScreen` / `Panel` / `PanelScrollBar` / `Button` / `TextBox` / `IntTextBox` / `Theme`；
* 视觉：`client/ui/ShopRender.java` 自研绘制原语（圆角矩形、垂直渐变、圆、三角、描边、ARGB 颜色工具），
  风格参考 SDM-UI-Lib 的原语清单，**未复制其代码**，也不依赖它；
* 布局：顶部标题 + 余额 + 商品计数 + 搜索框 → 分类页签 → 商品网格（图标 / 本地化名 / 买价 / 库存 / 卖价）→
  底部数量输入 + 购买 + 出售 + 状态栏；
* **搜索**：按本地化名或物品注册名子串匹配；搜索索引在快照装配时算一次，
  按键时只做子串比较，过滤结果按「分类 + 搜索词」缓存，每帧不重复扫描；
* **虚拟滚动**：只为可视窗口（上下各多一行）内的槽位创建控件，
  几何计算在 `client/ui/VirtualGrid.java`（纯整数、可离线自检）；
  滚动时若「首个可见行」变化才重建那 20~30 个控件，因此 10000 条与 30 条的每帧开销几乎相同；
  为配合 FTB 的 `PanelScrollBar`（它用 `panel.getContentHeight() - panel.getHeight()` 当滚动上限），
  `GridPanel` 覆盖了 `getContentHeight()`（返回逻辑内容高度）与 `setScrollY()`（窗口变化时重建控件）；
* **延迟加载**：客户端只在商店界面打开、或服务端明确要求打开时才装配数据；
  关闭界面（`onClosed`）即丢弃快照，10000 条商品不会常驻内存；
* 交易结果由服务端下发，游戏内聊天区与界面状态栏都会提示。

### 3.7 键位绑定（默认 O）

* 注册：`RegisterKeyMappingsEvent`（mod 事件总线，`ShopKeyMappings`）；
* 默认键 `GLFW_KEY_O`（79）。已核对 1.21.1 `Options` 的全部默认键位，
  **O 没有被任何原版绑定占用**，开箱即用不冲突；
* 分类是自定义的 `key.categories.better_minecraft_shop`（1.21.1 的分类就是这样一个翻译键字符串，
  原版控制菜单用 `Component.translatable(category)` 显示它）；
* 检查：`ClientTickEvent.Post` 中 **无条件** `consumeClick()` 清空队列
  （避免点击滞留到下一次打开界面时误触发），有任意界面打开时不抢按键；
* 冲突处理：`KeyConflictContext.IN_GAME` 让原版控制菜单在按键重复时标红提示；
  玩家可随时在「选项 → 控制 → 按键绑定 → 更好的 Minecraft 商店」里改成别的键，
  键位随原版 `options.txt` 存档。

### 3.8 大数据量（10000+）性能设计

| 环节 | 做法 |
|---|---|
| 配置解析 | 单次扫描 + 逐条 `Codec` 严格解析；10000 条的解析与去重是一次性成本（启动/重载时），日志给出毫秒耗时 |
| 内存索引 | `HashMap<UUID, 条目>` + `HashMap<String, 条目键>`，交易查找 O(1) |
| 快照组装 | `ShopDataCache` 按目录版本缓存分类数据与模板 `ItemStack`，同一版本内不重复复制 |
| 网络 | 每批 ≤500 条；交易后走增量补丁 |
| 客户端缓存 | 过滤结果缓存 + 搜索索引预计算（O(1) 取用，按键时一次 O(n) 子串扫描） |
| 渲染 | 虚拟滚动，只建可视窗口内的控件（`tools/VirtualGridCheck.java` 断言了「滚动一遍覆盖全部条目」与「窗口 ≤30 个控件」） |
| 重载 | `WatchService` 防抖整体重载，而不是每帧轮询文件时间戳 |

## 四、FTB Library 侧边栏集成（实测 schema，与需求文档示例不同）

需求文档给的示例含 `group` / `x` 字段，**那是更老版本的 schema**。本项目使用的前置是
FTB Library **2101.1.37**，其 `SidebarButtonData`（`dev.ftb.mods.ftblibrary.sidebar`）真实字段为：

| 字段 | 类型 | 说明 |
|---|---|---|
| `icon` | 数组 | `Icon.CODEC`（`ExtraCodecs.JSON`）；`.png/.jpg` 走 `ImageIcon`，否则走图集 |
| `click` | 字符串数组（≥1） | 每项 `scheme:path`，见下方点击链路 |
| `shift_click` | 字符串数组 | 可选，Shift 点击时执行 |
| `default_enabled` | 布尔 | 默认 `true` |
| `loading_screen` | 布尔 | 默认 `false`，点击时先显示 FTB 的加载屏 |
| `tooltip` / `shift_tooltip` | Component 数组 | 可选 |
| `requires_op` | 布尔 | 默认 `false` |
| `required_mods` | 字符串数组 | 任一前置缺失则隐藏按钮 |
| `sort_index` | 整型 | 默认 `0`，决定按钮顺序 |
| `environment_condition` | 字符串 | 可选，按环境变量显隐 |

本模组的 `assets/better_minecraft_shop/sidebar_buttons/shop.json`：

```json
{
  "icon": ["better_minecraft_shop:textures/shop_icon.png"],
  "sort_index": 50,
  "default_enabled": true,
  "loading_screen": false,
  "click": ["better_minecraft_shop:open_shop"],
  "tooltip": [{ "translate": "sidebar_button.better_minecraft_shop.open_shop.desc" }],
  "required_mods": ["ftblibrary"]
}
```

点击链路（全部来自真实反编译源码）：

1. `SidebarButtonManager`（`SimpleJsonResourceReloadListener`，目录名 `sidebar_buttons`）从
   **`assets/<命名空间>/sidebar_buttons/`** 扫描 JSON（与 FTB 自带的
   `assets/ftblibrary/sidebar_buttons/toggle/day.json` 同级），用 `SidebarButtonData.CODEC` 解析；
2. 点击 → `RegisteredSidebarButton#clickButton` → `Widget#handleClick(String)` 按第一个 `:` 拆 scheme/path
   → `ClientUtils#handleClick`；scheme 不在内置集合（http/https/file/command/static_method/custom）时
   走 default 分支，用完整的 `"better_minecraft_shop:open_shop"` 触发 Architectury 事件 `CustomClickEvent.EVENT`；
3. 客户端入口 `BmcsClient` 里 `ShopSidebarIntegration.register()` 注册该事件监听器，命中即发送
   `OpenShopPayload` 给服务端；**客户端不自行打开界面**；
4. 服务端校验后回发 `ShopDataPayload(openScreen = true)`，客户端再 `openGui()` 打开 `ShopScreen`。

> 需求文档提到的 `ClientUtils.registerClickEvent(...)` 在 2101.1.37 里**并不存在**；
> 真实入口是 `CustomClickEvent.EVENT.register(...)`。另外 SDMShop 本身**完全没有侧边栏集成**
> （jar 内无任何 `sidebar_buttons` 资源、常量池里也没有 FTB sidebar 类），所以这是**新功能**而非移植。

## 五、配置文件参考

1.0.5 起买入与卖出**分成两个平级目录**（都直接位于 `config/better-minecraft-shop/` 下）：

| 交易方向 | 目录 | 商品字段 |
|---|---|---|
| 玩家**买入**（花深索币买物品） | `config/better-minecraft-shop/in/**.json` | `price`（必填，≥1）、`stock`（可选，默认 `-1`） |
| 玩家**卖出**（把物品换成深索币） | `config/better-minecraft-shop/out/**.json` | `sell_price`（必填，≥1） |

* 启动时只 `Files.createDirectories(in)` / `createDirectories(out)`，**不写入任何默认 JSON**；
  仓库自带的 8 个旧格式模板已移到 `docs/examples/legacy-shop_items/`（只作文档与迁移参考，不打进 jar）。
* 旧数据（`config/better-minecraft-shop/shop_items/` 与单文件 `shop_items.json`）**不读、不改、不删**；
  检测到就打印一条 WARN，给出绝对路径并指向 `tools/migrate_shop_items.py`（默认预览，`--apply` 才写入）。
* 格式版本 `"version": 2`；`in/` 里写 `sell_price`、`out/` 里写 `price` 都会被忽略并打日志提示。

`in/weapons_tools.json`（玩家买入：`price` + `stock`，可带附魔）：

```json
{
  "version": 2,
  "categories": [
    {
      "id": "weapons_tools",
      "icon": "minecraft:diamond_sword",
      "items": [
        {
          "item": "minecraft:diamond_sword",
          "price": 6000, "stock": 4,
          "components": {
            "minecraft:enchantments": { "minecraft:sharpness": 5, "minecraft:unbreaking": 3 }
          }
        },
        {
          "item": "minecraft:netherite_chestplate",
          "price": 24000, "stock": 2,
          "components": {
            "minecraft:enchantments": { "minecraft:protection": 4, "minecraft:mending": 1 }
          }
        }
      ]
    }
  ]
}
```

`out/weapons_tools.json`（玩家卖出：只写 `sell_price`）：

```json
{
  "version": 2,
  "categories": [
    {
      "id": "weapons_tools",
      "icon": "minecraft:diamond",
      "items": [
        { "item": "minecraft:diamond_sword", "sell_price": 1500,
          "components": { "minecraft:enchantments": { "minecraft:sharpness": 5 } } },
        { "item": "minecraft:netherite_chestplate", "sell_price": 6000 }
      ]
    }
  ]
}
```

分类字段：

| 字段 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `id` | ✔ | — | 分类 id，转小写；商品键前缀（`<id>.<序号>`）；也是内置翻译键 `category.better_minecraft_shop.<id>` 的后缀 |
| `display_name` | ✘ | 空 | 分类展示名，支持翻译键；**留空即用内置翻译键**（推荐，默认模板全部留空） |
| `icon` | ✘ | 空 | 页签图标，物品 id |
| `priority` | ✘ | 查表 | 去重优先级，`0..100`，越大越优先；不写则查 `CategoryPriority` 内置表 |
| `editable` | ✘ | `false` | 游戏内是否可改性：`true` 才能改名 / 换图标 / 加删商品。游戏内新建的分类写 `true`，手写文件不写即为只读 |
| `items` | ✔ | — | 商品数组（可以为空：空分类保留并在页签上显示，方便往里加商品） |

游戏内新建的分类**一个分类一个 JSON 文件**，文件名 = 分类名（留空为 `_0`、`_1`…），
分类 `id` 固定为 `cat_0`、`cat_1`…（改名只改 `display_name` 与文件名，id 不变，库存记录因此不会丢）。

商品字段：

| 字段 | `in/` | `out/` | 说明 |
|---|---|---|---|
| `item` | ✔ | ✔ | 物品注册名 `命名空间:路径` |
| `price` | ✔ | ✘ | 买入单价，**必须 ≥ 1**；`out/` 里出现会被忽略并提示 |
| `sell_price` | ✘ | ✔ | 回收单价，**必须 ≥ 1**；不再用 `price` 兜底；`in/` 里出现会被忽略并提示 |
| `stock` | ✘ | ✘ | `-1` 不限量（默认）；`0` 暂时售罄；正数为限量初始值（**只影响买入**，卖出不限量） |
| `components` | ✘ | ✘ | **只支持附魔**：`DataComponentPatch` 里只认 `minecraft:enchantments` / `minecraft:stored_enchantments`，其余键忽略并提示 |
| ~~`max_stack`~~ | — | — | **已移除**：单次交易上限固定取物品堆叠上限（≤64） |
| ~~`variant`~~ | — | — | **已移除**：判重键只按「物品 id + 附魔签名」 |
| ~~`display_name`~~ | — | — | **已移除**：写了会被忽略并在日志提示 |

去重与商品键：

* 判重键 = `item` + `|` + 附魔的规范化 JSON（没有附魔时为空串）。
  因此**纯物品条目严格按 `item` 去重**（符合需求），而带附魔的条目是不同商品，不会被合并；
* 去重在**每个方向目录内部**进行；重复时保留优先级更高的分类，优先级相同保留先出现的
  （文件按路径排序，结果确定）；
* 商品键 = `<分类id>.<该分类内序号>`（买入）/ `sell.<分类id>.<该分类内序号>`（卖出），
  序号只取决于文件顺序与配置内容，调整价格 / 库存不会改变它，
  因此 `/bmcs stock set` 的键与存档库存不会错位；
* **跨目录防刷钱**：同一判重键如果 `out/` 的 `sell_price` 高于 `in/` 的 `price`，
  载入时把回收价压回 `price` 并打印提示（防止「买入再卖出」刷钱）。

其它：

* `components` 在 **`RegistryOps`（带注册表上下文）** 下解析，因此附魔这类需要查注册表的组件
  能正确还原；解析失败**只跳过这一条并报错**，不会静默丢附魔；
* **`components` 只支持附魔**：解析前会把 `components` 里除 `minecraft:enchantments` /
  `minecraft:stored_enchantments` 之外的键剔掉，并逐条打印「已忽略：…」提示。
  改名（`custom_name`）、`lore`、属性等组件因此不再生效，名字一律走游戏内置本地化（见 3.2）；
* 单个文件体积上限 **10MB**，超限拒绝加载；带 UTF-8 BOM 的文件会被自动兼容；
* 逐条报错只在日志里打印**前 40 条**，之后折叠成一行（避免一份系统性写错的配置刷爆日志），
  总数始终由「本次加载跳过 N 条」给出；
* 重载：改文件后自动热重载（防抖 1.5 秒），或 `/bmcs reload`；
* 空目录 = 空商店：`in/` 与 `out/` 都没有 JSON 时商店就是空的（strict empty；日志「商店为空（不会写入默认配置）」）；
  目录里**有文件但全部解析失败**时才保留上一份可用数据，避免一个笔误把商店清空；
* 游戏内新建（单人存档任何人可用，专用服务器需权限等级 2）：
  * 右上角只有「新建分类」一个按钮（仅编辑模式可见），搜索框最右，间距 6 px；「新建商品」是编辑模式下商品网格固定的第一格，仅在选中「游戏内新建的分类」时出现；
  * **先建分类再建商品**：分类名支持中英文、留空自动 `_0`/`_1`…、**分类名即文件名**、重名拒绝；
    图标选择器可搜索、可分页，列出全部已注册物品（含模组物品）；
  * 分类 id 固定 `cat_N`（改名不改 id，库存不丢），文件内写 `"editable": true`；
    **一个分类一个文件**，手写多分类文件照旧能加载，但游戏内只读；
  * 编辑模式（左侧栏「编辑」开关）：左键删商品（确认框）、右键分类页签改名 / 换图标
    （改名同步重命名文件；文件里还有别的分类时拒绝）；
  * 写盘：临时文件 → `.bak` 备份 → 原子替换（`CategoryFileIO`），成功后自动重载并刷新所有在线玩家；
  * 校验失败（价格 / 库存越界、重复条目、坏 JSON、只读）一律拒绝写入并在界面给出原因。

## 七、与 SDMShop 的差异（要点）

完整逐条对照见 `docs/SDMShop-缺陷对照表.md`。摘要：

| SDMShop 的问题 | 本模组的做法 |
|---|---|
| 目录由客户端上传 NBT 覆盖服务端并落盘，无权限校验 | 目录只来自服务端本地 JSON，客户端无写入通路 |
| 商品用列表下标寻址，`index = -1` 直接把服务端打崩 | 用稳定 UUID 寻址 + 目录版本校验，越界即拒绝 |
| `count` 无服务端校验，负数买入反而加钱 | 解码阶段 + 业务层双重范围校验 |
| 卖出先给钱、后删物品且丢弃删除结果（卖空气换钱） | 先移除物品，成功后才进账 |
| 买、卖都扣同一个 `limit`，越卖越少 | 买入扣减、卖出回收补货（不超上限） |
| 每次交易广播全服 + 全量写盘 | 只刷新发起者，且只发这条商品的增量补丁；库存交给 SavedData 原子落盘 |
| 附魔 / 改名在存档往返中丢失 | 全程 `DataComponent`/`ItemStack.copy()`，配置解析走 `RegistryOps` |
| 失败时静默丢条目（无日志、无隔离） | 逐条解析 + 精确报错 + 跳过单条；单个文件损坏只丢该文件；整目录不可读时保留上一份数据 |
| 依赖未声明，缺前置直接 `NoClassDefFoundError` | `neoforge.mods.toml` 显式声明 `ftblibrary` / `architectury` 为必需 |
| 商品列表一次性全塞进 GUI，条目多了直接卡死 | 虚拟滚动（只建可视窗口控件）+ 分批同步（每批 ≤500 条） |

### 8.4 兼容性测试

* **FTB Library 版本**：`2101.1.37` 实测加载；声明范围 `[2101.1.0,)`。
* **Architectury 版本**：`13.0.6` 实测加载；声明范围 `[13.0.6,)`。
* **专用服务器**：实测启动成功（`Done (…)`），无 FTB 客户端类被加载；
  客户端专用类只在 `@Mod(dist = CLIENT)` 入口与 `Dist.CLIENT` 事件里被引用。
* **多人并发**：库存与余额都在服务端主线程读写（网络 handler 由 NeoForge 的 `enqueueWork` 派发），
  两个玩家同时抢购同一件限量商品由 `ShopStockManager.consume` 的「先校验后扣减」保证不超卖。
* **单人 / 局域网**：客户端与服务端同 JVM；本模组不使用跨端共享的静态可变状态
  （客户端快照 `ShopClientData` 只在客户端主线程访问，服务端状态在 `ShopManager` / `SavedData`）。
* **存档往返**：库存与余额分别落在 `world/data/better_minecraft_shop_stock.dat` 与玩家实体附件里；
  配置升级不会让旧存档报错（`Codec` 缺字段有默认值）。
* **配置升级**：1.0.5 起只读 in/ 与 out/；旧数据用 tools/migrate_shop_items.py 迁移，源文件保留；
  旧的 `display_name` 字段被忽略但不再报错；商品键（库存索引）在价格调整后保持不变。

## 十、已知限制与可继续改进的点

1. **GUI 视觉未截图验证**（本机无显示环境，`runClient` 需要 OpenGL）。
   界面的结构、FTB API 调用签名、虚拟滚动几何都做了逐项核对与离线自检，但没有真实截图。
2. 商品单位固定为「1 件」：不支持“一捆 N 件按一份价格卖”。如需整捆售卖，在 `ShopItemEntry`
   增加 `bundle` 字段并在交易层乘算即可（改动集中在 3 个文件）。
3. 分类页签不支持拖拽排序；顺序由文件顺序与配置顺序决定。
4. 未做 FTB Teams / 权限组的经济集成（当前只有单一货币与通用命令）。
5. `max_stack` 字段已按需求移除（单次交易上限固定取物品堆叠上限，≤64）；如需再提供
   「一次交易发放 N 件」的自定义上限，可以重新加回该字段并在 `ShopItemEntry.tradeLimit()` 里参与裁剪。
6. 经济数据没有审计日志；如需，可在 `ShopTransaction` 成功路径加一行记录。
7. 热重载是**整体重载**（不是单文件增量）：去重优先级跨文件，增量更新容易产生
   「A 文件删了这条、B 文件的重复项该顶上来了」这类错误；10000 条的解析耗时在几十毫秒量级，
   整体重载更稳。
8. 按键冲突只做「有界面时不抢按键 + 交给原版控制菜单标红提示」；
   没有实现自定义的冲突裁决（例如“同键时优先本模组”）。
9. 滚轮在商店界面内任意位置都会滚动商品网格（FTB `PanelScrollBar` 的 `canAlwaysScroll` 行为），
   这是有意保留的交互，换成「仅网格上方可滚」只需去掉 `setCanAlwaysScroll(true)`。

## 十一、与需求文档的必要偏差（都有实测依据）

| 需求文档 | 实现 | 依据 |
|---|---|---|
| `mod_id: better-minecraft-shop` | modId `better_minecraft_shop`；jar 文件名与展示名保留连字符 | FML 4.0.42 `ModInfo.VALID_MODID = ^[a-z][a-z0-9_]{1,63}$`（连字符非法，会 `InvalidModFileException`）；`VALID_NAMESPACE` 才允许 `._-` |
| 侧边栏 JSON 含 `group` / `x` | 无这两个字段 | FTB Library 2101.1.37 的 `SidebarButtonData.CODEC` 里没有它们（`group`/`x` 属旧 schema） |
| `ClientUtils.registerClickEvent` | `CustomClickEvent.EVENT.register(...)` | 2101.1.37 里不存在 `registerClickEvent`；点击最终触发 `CustomClickEvent` |
| 「用 DataComponent 存玩家余额」 | 余额用 Data **Attachment**；物品数据全程用 DataComponent | DataComponent 是 ItemStack 的数据；实体存档对应 Attachment（Codec 序列化，随存档） |
| `common/` + `neoforge/` 双模块 | 单模块 | 仅面向 NeoForge，多模块只为跨 loader 增加复杂度 |
| 键位绑定的 `keybind` 包放 common 侧 | 放在 `com.lyhyy2007.bmcs.client` | 1.21.1 的 `KeyMapping` / `RegisterKeyMappingsEvent` / `ClientTickEvent` 都是客户端专属类，放 common 侧反而会把客户端类暴露给专用服务器 |
| 去重「以 item 字段为唯一标识」 | 判重键 = `item` + 附魔签名 | 纯物品条目因此**严格按 item 去重**（符合原文）；但若不区分附魔，「附魔锋利 V 的钻石剑」和「普通钻石剑」会被合并成一条，默认配置里就有这种商品。需要强制合并时把它们写成同样的附魔（或都不写）即可 |
| 分批同步「按分类分批，每批 ≤500 条」 | 实现为**按条目切片** 500 条/批 | 一个分类可能有上万条（`gen_stress_config.py` 生成的默认就是 8 个分类 10000 条），按分类分批无法保证单包不超 1MB 上限；按条目切片与「每批 ≤500 条」的硬要求一致 |
| 分类名也要求移除 `display_name` | 分类的 `display_name` 保留为可选覆盖，但默认模板全部省略，改用内置键 `category.<mod>.<分类id>` | 需求 2.8 的示例 JSON 里分类仍带 `display_name`；保留它可用于「不想改语言文件就改分类名」的场景，同时默认路径已经是纯本地化 |
| SDMShop 源码作为移植基础 | 仅作缺陷分析参考 | SDMShop 无侧边栏、货币委托外部模组、目录由客户端上传，其架构不适用于本需求 |
